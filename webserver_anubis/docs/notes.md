See [Environment variables](https://anubis.techaro.lol/docs/admin/installation#environment-variables) for details

`anubis_version` sets the tag of the image `ghcr.io/techarohq/anubis`, `latest` by default.

### Environment

Anubis is configured with environment variables, see the table linked above.
All variables are set with `anubis_environment`, which is merged over the defaults of the role.

The role requires the following variables and checks them before it changes anything:

| Variable | Default of the role | Description |
|---|---|---|
| `BIND` | `:8923` | Address Anubis listens on, use the port in the labels of a reverse proxy |
| `BIND_NETWORK` | `tcp` | Address family of `BIND` |
| `POLICY_FNAME` | `/data/cfg/botPolicies.yaml` | Path of the bot policy generated by the role inside the container |
| `TARGET` | – | URL of the protected service, has to be set |

Anubis runs behind a reverse proxy, e.g. Traefik, and expects the address of the client in the header `X-Real-Ip`,
requests without it are answered with 500 as misconfiguration.

```yaml
anubis_environment:
  TARGET: 'http://192.168.99.21:80'
  COOKIE_DYNAMIC_DOMAIN: 'true'
  SERVE_ROBOTS_TXT: 'true'
  WEBMASTER_EMAIL: 'webmaster@example.org'
```

### Secrets

Variables carrying secrets, e.g. `ED25519_PRIVATE_KEY_HEX`, are not set in `anubis_environment`, but as podman secrets with `anubis_secrets`.
Every secret has a `name`, the `data` and the `target`, the usual name of the variable.
The role creates the secret with `podman secret create`, mounts it to `/run/secrets/<name>` and sets `ED25519_PRIVATE_KEY_HEX_FILE`,
so the key is neither part of the quadlet unit nor of the environment of the container:

```yaml
anubis_secrets:
  - name: 'anubis_ed25519_private_key'
    data: "{{ vault_anubis_ed25519_private_key }}"
    target: 'ED25519_PRIVATE_KEY_HEX'
```

A `target` and its file variable must not be set in `anubis_environment`, the role checks this.
`ED25519_PRIVATE_KEY_HEX` is the only allowed secret.
`HS512_SECRET` has no file variable in Anubis, it would be part of the environment, the role rejects it as secret and in the environment.

### Allowed variables

The role only allows the environment variables in `webserver_anubis__environment_allowed` and the secret with the target `ED25519_PRIVATE_KEY_HEX`,
it stops before any change if unknown variables or secrets are set.
This prevents unexpected behavior by accident, e.g. by a typo or a variable that has to be passed as secret.
The check uses the environment and the secrets of the container after merging `anubis_container`,
so variables set with `anubis_container.environment` are checked as well.
The allowed variables are the variables of Anubis v1.28.2 (`installation.mdx` and the flags of `cmd/anubis/main.go`)
without the secrets, the variables of BotStopper, the command line modes and the deprecated `THOTH_*`,
and the file variable `ED25519_PRIVATE_KEY_HEX_FILE`. The role sets it from `anubis_secrets`, it must not be set in `anubis_environment`.

### Container

Ports, volumes, additional hosts (`etc_hosts`) and dependencies (`requires`) are changed with `anubis_container`, it is merged over the default of the container.
The merge is not recursive, `publish` and `volumes` replace the values of the default completely,
`anubis_container.environment` replaces the environment including `anubis_environment`, use `anubis_environment` instead.

### Validation

The role checks before any change that `anubis_secrets` is a list of entries with `name`, `data` and `target` and unique names,
that the required variables are set, that neither a secret nor its file variable is set in `anubis_environment`
and that only allowed variables and secrets are used.
If `anubis_container` or `anubis_config` is no dictionary, merging it with the default fails before anything changes.

### Migration from the single variables

The former single variables were removed, set the environment variables in `anubis_environment` instead:

| Former variable | Environment variable |
|---|---|
| `anubis_port`, `anubis_bind` | `BIND` |
| `anubis_bind_network` | `BIND_NETWORK` |
| `anubis_cookie_dynamic_domain` | `COOKIE_DYNAMIC_DOMAIN` |
| `anubis_policy_fname` | `POLICY_FNAME` |
| `anubis_redirect_domains` | `REDIRECT_DOMAINS` (comma separated) |
| `anubis_serve_robots_txt` | `SERVE_ROBOTS_TXT` |
| `anubis_socket_mode` | `SOCKET_MODE` |
| `anubis_strip_base_prefix` | `STRIP_BASE_PREFIX` |
| `anubis_target` | `TARGET` |
| `anubis_xff_strip_private` | `XFF_STRIP_PRIVATE` |

The role does not set `COOKIE_DYNAMIC_DOMAIN`, `SERVE_ROBOTS_TXT`, `SOCKET_MODE`, `STRIP_BASE_PREFIX` and `XFF_STRIP_PRIVATE` anymore, Anubis uses the same defaults.

### Bot policy

The bot policy is written to `anubis_home/botPolicies.yaml` and mounted into the container.
`anubis_config` is merged over the default policy, every key replaces the key of the default completely, e.g. `bots` replaces the list of rules.
The default policy allows the networks in `anubis_trusted_hosts` without challenge, only the loopback addresses by default:

```yaml
anubis_trusted_hosts:
  - '192.168.99.0/24'
  - 'fd00::99:0/112'
```

### Restarts and updates

A running container is restarted when `botPolicies.yaml`, a secret or the quadlet unit changed, the first start of the container does not trigger an additional restart.
Updates of the image are done by `container_update` with `anubis_autoupdate_enabled: true` and `anubis_autoupdate_schedule`.

### Migration of the container role

- The global variable `trusted_hosts` is replaced by `anubis_trusted_hosts`, set it to the former value.
- `anubis_config` was a replacement of the default policy, now it is merged over it per key, set `bots` to replace the rules.
- `anubis_container` replaced the default container completely, now it is merged over it.
- The secret of `ED25519_PRIVATE_KEY_HEX` is mounted as file and read with `ED25519_PRIVATE_KEY_HEX_FILE`, before it was passed as environment variable, `anubis_secrets` stays the same.
- `anubis_version` sets the tag of the image, before it was always `latest`.
- `podman___update_mode` is not evaluated anymore, the role neither stops the container nor pulls the image or recreates the container, the bot policy is always written.
- The tags are `webserver` and `webserver_anubis`.

### Tests

The molecule scenario `default` runs the role in two [tart](https://tart.run) VMs on a macOS controller, the base VM has to be Debian 13.
The base VM is cloned for every platform and the clones are deleted afterwards, the base VM itself is never changed.
The playbooks creating and destroying the VMs are shared by all tart scenarios and live in `.molecule/tart/` in the repository root.

| Platform | Test case |
|---|---|
| `molecule-anubis-ipv4-only` | Container with IPv4 address only |
| `molecule-anubis-ipv6` | Container with IPv4 and IPv6 address, an additional variable in `anubis_environment` and a secret in `anubis_secrets` |

`prepare` sets up podman and the network `podman-molecule` with the role `container_podman` and pulls the image.
`side_effect` runs the role with `anubis_container` not a dictionary, a secret without data, without `TARGET`, the key and `HS512_SECRET` in the environment,
an unknown environment variable in `anubis_environment` and in `anubis_container.environment` and an unknown secret
and checks that it fails with the expected message and the quadlet unit and the bot policy are unchanged (tasks marked `expect ERROR`),
then it changes `DIFFICULTY` on `molecule-anubis-ipv6`, the quadlet unit changes and Anubis has to restart.
`verify` checks the quadlet unit with the mounted secret, the bot policy with `anubis_trusted_hosts`, the service, the podman secrets,
the container addresses and the environment with `ED25519_PRIVATE_KEY_HEX_FILE` and without the key,
and requests Anubis as browser behind a reverse proxy (`X-Real-Ip`), it has to answer with its challenge.
The VMs need access to `ghcr.io` for the image.

Requirements on the controller: `tart`, `sshpass` (`brew install hudochenkov/sshpass/sshpass`), `molecule` and the collection `containers.podman`.

| Environment variable | Default | Description |
|---|---|---|
| `MOLECULE_TART_IMAGE` | `ghcr.io/cirruslabs/debian:latest` | Base VM or image that is cloned |
| `MOLECULE_TART_USER` | `admin` | SSH user of the base VM |
| `MOLECULE_TART_PASSWORD` | `admin` | Password of the SSH user, used to install the SSH key and for `sudo` |

```shell
cd webserver_anubis
MOLECULE_TART_IMAGE='debian' molecule test
```
