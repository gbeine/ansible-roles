FreeScout runs in the container image [nfrastack/container-freescout](https://github.com/nfrastack/container-freescout) (`latest` by default) as podman quadlet.
The image contains nginx, PHP-FPM and FreeScout, the web interface listens on port 80.
Below `freescout_home` the role creates `data` (mounted to `/data`, configuration, application key, sessions, uploads and modules)
and `logs` (`/logs`, logs of nginx, PHP and the scheduler).
FreeScout needs a MySQL, MariaDB or PostgreSQL database, the role does not create it.

### Configuration

FreeScout is configured completely with environment variables in `freescout_environment`, merged over the default of the role.
The default sets `TIMEZONE` to `freescout_timezone` and references the passwords of the admin and the database with
`ADMIN_PASS_FILE` and `DB_PASS_FILE` from the secrets `freescout_admin_password` and `freescout_database_password`.
Values are strings, e.g. `'TRUE'`.

The role requires the following variables and checks them before it changes anything:

- `APP_URL`, the full external URL, e.g. `https://helpdesk.example.org`
- `ADMIN_EMAIL`, the admin created by the first start with an empty database
- `DB_HOST`, `DB_NAME` and `DB_USER`

The variables of the image (`SETUP_TYPE`, `ADMIN_*`, `DB_*`, `ENABLE_AUTO_UPDATE`, `SCHEDULER_*`, `WORKER_LOG_*`)
are described in the [README of the image](https://github.com/nfrastack/container-freescout#environment-variables).
`DB_TYPE` is `mysql` by default, which works for MariaDB as well, `pgsql` selects PostgreSQL.
`ADMIN_EMAIL`, `ADMIN_FIRST_NAME`, `ADMIN_LAST_NAME` and the password are only used while the database is empty.
The first start migrates the database and creates the admin afterwards, the web interface is available when both are done.
If the container is restarted before, e.g. by a second run of the role with changes, the database is not empty anymore at the next start
and the admin is never created. Create it then with
`podman exec freescout sudo -H -u nginx php /www/html/artisan freescout:create-user --role=admin --firstName=<first> --lastName=<last> --email=<email> --password=<password>`.

Every other setting of FreeScout is set with `FREESCOUT_<KEY>`, the image writes it as `<KEY>` to the `.env` file of FreeScout,
the value `unset` removes the key. The keys are the ones of the `.env` file of FreeScout, e.g. `MAIL_HOST`, `APP_LOCALE` or `APP_TRUSTED_PROXIES`.

```yaml
freescout_environment:
  APP_URL: 'https://helpdesk.example.org'
  ADMIN_EMAIL: 'admin@example.org'
  DB_HOST: 'mariadb'
  DB_NAME: 'freescout'
  DB_USER: 'freescout'
  FREESCOUT_APP_LOCALE: 'de'
  FREESCOUT_APP_TRUSTED_PROXIES: '10.89.0.0/24'
  FREESCOUT_MAIL_DRIVER: 'smtp'
  FREESCOUT_MAIL_HOST: 'mail.example.org'
  FREESCOUT_MAIL_PORT: '587'
  FREESCOUT_MAIL_ENCRYPTION: 'tls'
  FREESCOUT_MAIL_USERNAME: 'helpdesk@example.org'
  FREESCOUT_MAIL_PASSWORD_FILE: '/run/secrets/freescout_mail_password'
```

At every start the image writes `APP_URL`, the database, `APP_TIMEZONE` from `TIMEZONE`, `APP_TRUSTED_HOSTS` from the host of `APP_URL`,
`SESSION_SECURE_COOKIE` for `https`, `APP_LOG` and `APP_DISABLE_UPDATING` to the `.env` file, `FREESCOUT_<KEY>` is applied afterwards.
Updates of FreeScout come with new images, with `ENABLE_AUTO_UPDATE` (`TRUE` by default) the image migrates the database after an update.

### Secrets

`freescout_secrets` is a list of podman secrets with `name` and `data`, each one is mounted to `/run/secrets/<name>` in the container.
The environment references them with `<VARIABLE>_FILE`, the image reads the file at the start,
so passwords are neither part of the quadlet unit nor of the environment of the container.
Passwords cannot be set in plain text, the allowed variables only contain the variants with `_FILE`.

```yaml
freescout_secrets:
  - name: 'freescout_admin_password'
    data: "{{ vault_freescout_admin_password }}"
  - name: 'freescout_database_password'
    data: "{{ vault_freescout_database_password }}"
  - name: 'freescout_mail_password'
    data: "{{ vault_freescout_mail_password }}"
```

The application key is generated by the first start and stored in `data`,
`APP_KEY_FILE` with the secret `freescout_app_key` sets it, e.g. after moving an installation.

### Allowed variables

The role only allows the environment variables in `app_freescout__environment_allowed` and the secrets in `app_freescout__secrets_allowed`,
it stops before any change if unknown variables or secrets are set.
This prevents unexpected behavior by accident, e.g. by a typo or a variable that has to be passed as secret.
The check uses the environment and the secrets of the container after merging `freescout_container`,
so variables set with `freescout_container.environment` and secrets set with `freescout_container.secrets` are checked as well.

Allowed environment variables:

- the variables of the image listed above, the passwords only as `ADMIN_PASS_FILE`, `DB_PASS_FILE` and `APP_KEY_FILE`
- `TIMEZONE` of the base image, the other variables of the base images (`NGINX_*`, `PHP_*`, `CONTAINER_*`) are not allowed
- `FREESCOUT_<KEY>` for every key read by `config/*.php` of FreeScout 1.8.250, except the keys the image writes itself
  (`APP_URL`, `APP_TIMEZONE`, `APP_KEY`, `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`) and `DB_TEST_*`
- passwords and secrets of FreeScout only as `FREESCOUT_<KEY>_FILE`, e.g. `FREESCOUT_MAIL_PASSWORD_FILE` or `FREESCOUT_IMAP_PASSWORD_FILE`

`DATA_PATH`, `CONFIG_PATH`, `CONFIG_FILE`, `MODULES_PATH` and `ENABLE_*_REDIRECTION` are not allowed, they depend on the volumes of the role.
New versions of FreeScout may add keys, the list in `defaults/main.yml` is generated again from the `config` directory of the FreeScout version of the image.

Allowed secrets, the names of the secrets, the files below `/run/secrets`, the name has to match exactly:

- `freescout_admin_password`
- `freescout_database_password`
- `freescout_app_key`
- `freescout_mail_password`
- `freescout_imap_password`

### Container

Ports, volumes, additional hosts (`etc_hosts`) and dependencies (`requires`) are changed with `freescout_container`, it is merged over the default of the container.
The merge is not recursive, `publish` and `volumes` replace the values of the default completely,
`freescout_container.environment` replaces the environment including `freescout_environment`, use `freescout_environment` instead.
For a reverse proxy, e.g. Traefik, the labels are set with `freescout_labels`.

### Validation

The role checks before any change that only allowed environment variables and secrets are set in the container,
that the required environment variables are set and not empty, that the entries of `freescout_secrets` have `name` and `data`
and that every secret referenced by a `<VARIABLE>_FILE` below `/run/secrets` exists in `freescout_secrets`.
If `freescout_container` is no dictionary, merging it with the default fails before anything changes,
the same applies to a failing template in the variables, e.g. an unknown filter.

### Restart and updates

FreeScout is restarted if it was running and a secret or the quadlet unit changed, e.g. after changing `freescout_environment`, otherwise it is started and enabled.
Updates of the image are done by `container_update` with `freescout_autoupdate_enabled: true` and `freescout_autoupdate_schedule`,
without `freescout_autoupdate_schedule` the schedule of `container_update` is used.

### Migration

The single variables of former versions are replaced by `freescout_environment` and `freescout_secrets`:

- `freescout_url` is `APP_URL`
- `freescout_db_host`, `freescout_db_port`, `freescout_db_type`, `freescout_db_name` and `freescout_db_user` are
  `DB_HOST`, `DB_PORT`, `DB_TYPE`, `DB_NAME` and `DB_USER`, the former defaults `freescout` for the name and the user have to be set
- `freescout_db_pass` is the secret `freescout_database_password`
- `freescout_admin_email`, `freescout_admin_first_name` and `freescout_admin_last_name` are `ADMIN_EMAIL`, `ADMIN_FIRST_NAME` and `ADMIN_LAST_NAME`
- `freescout_admin_pass` is the secret `freescout_admin_password`
- `freescout_enable_auto_update` is `ENABLE_AUTO_UPDATE` (`'TRUE'` or `'FALSE'`)
- `freescout_mail_host` is `FREESCOUT_MAIL_HOST`

The names of the secrets stay the same, they are mounted as files now instead of being passed as environment variables.
The former role set `APP_TIMEZONE`, which the image ignores, and `FREESCOUT_APP_TIMEZONE`, which overwrote the timezone the image writes from `TIMEZONE`.
Now `TIMEZONE` is set to `freescout_timezone`, the image writes it as `APP_TIMEZONE`, `FREESCOUT_APP_TIMEZONE` is not allowed anymore.
The environment in `freescout_container.environment` is replaced by `freescout_environment`.
`podman___update_mode` is not evaluated anymore, the role neither stops the container nor pulls the image or recreates the container.
The tag `app_freescout` stays, the tag `app` is added.

### Tests

The molecule scenario `default` runs the role in two [tart](https://tart.run) VMs on a macOS controller, the base VM has to be Debian 13.
The playbooks creating and destroying the VMs live in `.molecule/tart/` in the repository root.

| Platform | Test case |
|---|---|
| `molecule-freescout-default` | Only the mandatory variables and the secrets of the admin and the database |
| `molecule-freescout` | IPv6, labels, `ADMIN_FIRST_NAME`, `FREESCOUT_APP_LOCALE`, the mail server and its password from a secret with `FREESCOUT_MAIL_PASSWORD_FILE` |

`prepare` creates the podman network, pulls the images and starts a MariaDB container as database.
`side_effect` runs the role with `freescout_container` not a dictionary, an empty `APP_URL`, a secret without `data`, without the secret of the database password,
the admin password in the environment, an unknown environment variable in `freescout_environment` and in `freescout_container.environment` and an unknown secret
and checks that it fails with the expected message and the quadlet unit is unchanged (tasks marked `expect ERROR`),
then it waits until the first start of FreeScout on `molecule-freescout` has finished and changes `FREESCOUT_APP_LOCALE`,
the quadlet unit changes and FreeScout has to restart.
`verify` checks the quadlet unit with the mounted secrets, the service, the directories, the addresses and the environment of the container without passwords,
waits until the login page is served, logs in as admin and checks the `.env` file of FreeScout, e.g. `APP_TIMEZONE`, `APP_LOCALE` and `MAIL_PASSWORD`.

| Environment variable | Default | Description |
|---|---|---|
| `MOLECULE_TART_IMAGE` | `ghcr.io/cirruslabs/debian:latest` | Base VM or image that is cloned |
| `MOLECULE_TART_USER` | `admin` | SSH user of the base VM |
| `MOLECULE_TART_PASSWORD` | `admin` | Password of the SSH user, used to install the SSH key and for `sudo` |

```shell
cd app_freescout
MOLECULE_TART_IMAGE='debian' molecule test
```
