# Rules for refactoring the roles

The roles are migrated and modernized one at a time. These rules apply to every role that is refactored.

## Workflow

- Never commit or push, and never propose a commit in a plan. The user commits.
- No file operations with git: no `git stash`, `git rm`, `git mv`, `git checkout` or `git restore` of files. Remove files with `rm`.
- After every implementation enter plan mode again. Never leave plan mode on your own, use ExitPlanMode only to get a plan approved.
- One role at a time. The user runs molecule, give the commands, e.g. `cd <role> && molecule test; cd ..`.
- Fix the role, never the filters of `common_filters`.
- Do not touch `meta/main.yml`.
- Additional Alpine packages are installed as described in the global CLAUDE.md.

## Variables

- `defaults/main.yml` is the interface of a role.
  - Inventory variables are named `<short>_*` (e.g. `grafana_*`), role variables `<role>__*` (e.g. `app_grafana__*`).
  - The file starts with the header "Do not edit this file" and the URL `https://ansible-roles.org/roles/<name>`,
    the internal values follow below "Defaults - do not change".
  - Mandatory values use `| mandatory`, optional ones `| default(...)`.
- Tasks and templates only use `<role>__*`.
  `common_globals__*` only appears in `defaults/*`, mapped to variables of the role, `site_*` is never used.
- A configuration is one dictionary in one line:
  `<role>__config: "{{ <role>__config_default | combine(<short>_config | default({})) }}"`.
  - No intermediate variables and no own check for a mapping, `combine` fails by itself.
  - Additional sources (e.g. `common_globals`) are additional `combine` in the same line.
  - An inventory variable with another name (e.g. `_settings`) is renamed to `_config`.
- Values of a configuration dictionary follow `time_chrony`:
  a string or number writes `key=value`, a list writes one line per element, `true` writes the option without value,
  `false` or `null` removes the option.
- Options of the role itself (e.g. `enabled`) are listed in `<role>__role_options` in `vars/main.yml` and never written to the file.
- Single variables for options are removed, the migration in `docs/notes.md` maps the former variables.

## Podman roles

- The container is `<role>__podman_container_default | combine(<short>_container | default({}))`, the merge is not recursive.
- `volumes`, `publish`, `command` and flags are only changed with `<short>_container`, there are no own variables for them.
- Environment:
  - `<role>__environment: "{{ <role>__environment_default | combine(<short>_environment | default({})) }}"`
  - mandatory variables are listed in `<role>__environment_required`
- Allow lists:
  - `container.environment` contains only variables listed in `<role>__environment_allowed`,
    the list contains all allowed variables including the file variables of the secrets, but not the targets of the secrets
  - exact names only, no regular expressions; names that an image composes from a key are generated (see Composed names)
  - checked on `<role>__container` after merging `<short>_container`, unknown names stop the role before any change
  - generated lists get a comment with source and version, e.g. "Generated from conf/defaults.ini of Grafana v13.3.1"
- `podman___update_mode` is removed. The service is restarted only if it was running and a secret or the quadlet unit changed,
  otherwise it is started. Updates are done by `container_update` with `<short>_autoupdate_enabled` and `<short>_autoupdate_schedule`.
- Tags are the category and the role, e.g. `[ 'app', 'app_grafana' ]`.

### Secrets

- `<short>_secrets` is a list of entries with `name`, `data` and `target`, the target is the usual name of the variable (e.g. `DB_PASSWORD`).
  The role creates every entry with `podman secret`, a changed secret restarts the running service.
- The task "Validate the secrets" runs directly after "Render the configuration" and reports
  "`<short>_secrets` has to be a list", "`<short>_secrets` entries need name, data and target"
  and "the names of `<short>_secrets` have to be unique".
- The expression for `secrets` in the container default only uses entries that are mappings with the keys it needs
  and is `omit` if `<short>_secrets` is empty or no list, broken entries are reported by the validation, not by "Render the configuration".
- Mandatory targets are listed in `<role>__secrets_required`, the message is "<App> needs the secrets …, missing: …".
- Neither a target nor a file variable may be set in `<short>_environment`, passwords are never part of the environment in plain text.
- Secrets are passed as files, `type=env` is only used if the image cannot read a file.

Secrets as files (the default):

- The secrets are mounted with `type=mount` to `<role>__secrets_dir` (`/run/secrets`), each as `/run/secrets/<name>`.
- `<role>__secret_files` maps every allowed target to its file variable, the form of the file variable is the one the image reads,
  e.g. `DB_PASSWORD: DB_PASSWORD_FILE`, `GF_SMTP_PASSWORD: GF_SMTP_PASSWORD__FILE` or `APP_KEY: FILE__APP_KEY`.
  The keys of `<role>__secret_files` are the allowed targets.
- `<role>__environment_secrets_files` computes `{file variable: /run/secrets/<name>}` from `<short>_secrets`,
  the container default sets `environment: "{{ <role>__environment | combine(<role>__environment_secrets_files) }}"`.
- `<role>__secret_variables` is `<role>__secret_files.keys() | list`.
  Variables carrying secrets the image cannot read from a file are added to the list,
  they are rejected as target and in `<short>_environment`.
- `<role>__environment_allowed` contains the file variables, not the targets.

Secrets in the environment (only if the image cannot read a file):

- The secrets are passed with `type=env,target=<target>`, there is no `<role>__secret_files`.
- `<role>__secrets_allowed` lists the allowed targets, they are not part of `<role>__environment_allowed`.
- "Validate the allowed environment variables and secrets" reads the targets from `<role>__container.secrets`
  and reports unknown targets as "Unknown secrets: …".
- The section Secrets of `docs/notes.md` explains why the image cannot read the secrets from files.

### Composed names

- If an image composes names from a free key (e.g. `<PREFIX>_<KEY>_<OPTION>`), the inventory declares the keys in `<short>_keys`,
  a dictionary with one list of keys per family, the default is `{}`. The families are listed in `<role>__keys_families`.
- The task "Validate the keys" runs before "Validate the secrets" and reports if `<short>_keys` is no dictionary,
  unknown families together with the allowed ones, families that are no list, invalid keys together with the allowed characters
  and duplicate keys.
- The role generates the exact names from the valid keys:
  `<role>__environment_allowed` is the fixed list `<role>__environment_allowed_options` plus the generated `<role>__environment_allowed_keys`,
  `<role>__secret_files` is the fixed mapping `<role>__secret_files_options` combined with the generated `<role>__secret_files_keys`.
- The message about unknown variables says that options with keys in their names need the keys in `<short>_keys`.
- `docs/notes.md` has a section "Options with keys" with a table of the families and the generated names and an example.

### Multiple instances

- `tasks/loop.yml` runs the role with `include_role` for every entry of `<short>_instances`,
  with `loop_var: '<short>'` and the hostname as `label`.
- Every entry takes the variables without the prefix `<short>_` (e.g. `home`, `ip`, `environment`, `secrets`),
  `tasks/loop.yml` sets the variables `<short>_*` from them, missing keys fall back to the defaults of the role.
- Every instance needs its own container name (`container.name`) and its own secret names.
- `docs/notes.md` has a section "Multiple instances" with the include of `tasks/loop.yml` in a play and an example of `<short>_instances`.
- The molecule scenario `loop` deploys two instances in one VM, one with IPv4 only and one with IPv6,
  `verify` checks every instance like the scenario `default` and that every quadlet unit only contains the secrets of its own instance.

## OpenWrt roles

- The platform is detected with `raw` (`/etc/openwrt_release`), plays for OpenWrt need `gather_facts: false`.
  Platform values live in `vars/Debian.yml` and `vars/OpenWrt.yml`, the tasks in `tasks/debian.yml` and `tasks/openwrt.yml`.
- OpenWrt uses the modules of `community.openwrt`: `init`, `ping`, `apk` or `opkg`, `slurp`, `copy`, `uci`, `service`.
- `enabled` is always supported: it is written to UCI and controls the service
  (`true` started and enabled, `false` stopped and disabled), even if the init script does not read it.
- Before any change the role stores the file and the UCI configuration on the controller in `<playbook_dir>/backups/<inventory_hostname>/`.
- In check mode the role stops after the installation if the package is missing.
- Do not restart with `restarted` if the old process may still hold the ports: stop, wait until the process has ended, then start (see `app_coturn`).

## Validation

- All checks run before any change.
- The task "Render the configuration" evaluates the variables once, failing templates and `combine` stop the role there.
- Checks collect the failures in a list `errors`, the message only names the failing checks.
- Names are checked with `<role>__name_pattern` unless an allow list exists.
- Line breaks in values and booleans that are no booleans are rejected.

## Documentation

- `README.md` keeps its front matter, the text is "Installs and configures …".
- `docs/notes.md` describes behavior, examples, validation, migration and tests,
  for podman roles the sections Configuration, Secrets, Allowed variables, Container, Validation, Restart and updates, Migration, Tests.
  - The section about allowed variables says that the lists prevent unexpected behavior by accident.
  - No tables of the variables of `defaults/main.yml`, they are generated. Tables of container variables or of `MOLECULE_TART_*` are fine.
  - The migration maps every former variable and names fixed bugs and changed behavior.
- Documentation and comments are written in English.

## Molecule tests

- The VMs are created with tart by `.molecule/tart/create.yml` and `destroy.yml`.
  Two platforms: `molecule-<short>-default` with the mandatory values only and `molecule-<short>` with the options.
- Test cases live in `test_cases.yml` with `role_vars`, `side_effect.role_vars` and `expect`.
- Sequence: destroy, syntax, create, prepare, converge, idempotence, side_effect, verify, destroy.
- `prepare` starts the services the role needs, e.g. a database (see `app_bookstack`).
- `side_effect`:
  - invalid runs are named "(expect ERROR)" and use `tasks/invalid_run.yml`,
    they check the message and that the md5 of the checked files is unchanged
  - afterwards a valid change on `molecule-<short>`, the service has to restart
- `verify` checks files and permissions, the service, ports and environment and a real function, e.g. a login, the API or a STUN request.
