linkding runs in the container image [sissbruecker/linkding](https://hub.docker.com/r/sissbruecker/linkding) (`latest` by default) as podman quadlet,
the web interface and the API listen on port 9090. The variants with Chromium for snapshots are selected with the version, e.g. `linkding_version: 'latest-plus'`.
Below `linkding_home` the role creates `data`, mounted to `/etc/linkding/data`: the SQLite database, the secret key (`secretkey.txt`,
generated by the image on the first start), the favicons, the previews and the assets.
`bootstrap.sh` of the image runs as root, migrates the database, gives `data` to `www-data` (UID 33) and starts uwsgi as `www-data`.

### Configuration

linkding has no configuration file, it reads its options only from the environment (`bookmarks/settings/base.py`, `bootstrap.sh` and `uwsgi.ini`).
The options are set in `linkding_environment`, merged over the default of the role, see the [options](https://linkding.link/options/).
The default sets `TZ` to `linkding_timezone`, linkding reads the time zone from `TZ` and uses UTC without it.
`null` removes a variable, e.g. `TZ: ~`.

```yaml
linkding_environment:
  LD_CSRF_TRUSTED_ORIGINS: 'https://linkding.example.org'
  LD_SESSION_COOKIE_AGE: 604800
  LD_ENABLE_SNAPSHOTS: true
  LD_DB_ENGINE: 'postgres'
  LD_DB_HOST: 'postgresql'
  LD_DB_OPTIONS:
    sslmode: 'disable'
```

The values are YAML values, the role writes the spelling linkding expects:

- booleans are `true` or `false` without quotes, the role writes `True` or `False`,
  `LD_DISABLE_REQUEST_LOGS` and `LD_LOG_X_FORWARDED_FOR` as `true` or `false` (`uwsgi.ini` compares with `true`)
- `LD_DB_PORT`, `LD_PREVIEW_MAX_SIZE`, `LD_REQUEST_MAX_CONTENT_LENGTH`, `LD_REQUEST_TIMEOUT`, `LD_SESSION_COOKIE_AGE` and `LD_SNAPSHOT_PDF_MAX_SIZE` are integers,
  `LD_SINGLEFILE_TIMEOUT_SEC` is a number
- `LD_DB_OPTIONS` is a dictionary, the role writes it as JSON
- `LD_DB_ENGINE` is `sqlite` (default of linkding) or `postgres`

`bookmarks/settings/custom.py` of the image is a Python file for own settings, the role does not support it.

### OIDC

With `LD_ENABLE_OIDC: true` linkding offers the login with OIDC, it needs the endpoints of the provider, the client and the secret of the client:

```yaml
linkding_environment:
  LD_ENABLE_OIDC: true
  OIDC_OP_AUTHORIZATION_ENDPOINT: 'https://sso.example.org/realms/main/protocol/openid-connect/auth'
  OIDC_OP_TOKEN_ENDPOINT: 'https://sso.example.org/realms/main/protocol/openid-connect/token'
  OIDC_OP_USER_ENDPOINT: 'https://sso.example.org/realms/main/protocol/openid-connect/userinfo'
  OIDC_OP_JWKS_ENDPOINT: 'https://sso.example.org/realms/main/protocol/openid-connect/certs'
  OIDC_RP_CLIENT_ID: 'linkding'
linkding_secrets:
  - name: 'linkding_oidc_client_secret'
    data: "{{ vault_linkding_oidc_client_secret }}"
    target: 'OIDC_RP_CLIENT_SECRET'
```

The redirect URI of the client at the provider is `<public URL>/oidc/callback/`, `LD_CSRF_TRUSTED_ORIGINS` has to contain the public URL behind a reverse proxy with HTTPS.

### Secrets

`linkding_secrets` is a list of podman secrets with `name`, `data` and `target`, the target is the variable of linkding.
linkding reads its options only from the environment and has no file variables (`bookmarks/settings/base.py` of linkding v1.47.0),
so the secrets are passed in the environment of the container with `type=env,target=<target>`, they are not part of the quadlet unit.
The allowed targets are `LD_DB_PASSWORD` and `OIDC_RP_CLIENT_SECRET`, they must not be set in `linkding_environment`.
The secret key of Django is generated by the image in `data/secretkey.txt`, keep it with the data.

```yaml
linkding_secrets:
  - name: 'linkding_db_password'
    data: "{{ vault_linkding_db_password }}"
    target: 'LD_DB_PASSWORD'
```

### Administrator

`linkding_admin` is the administrator with `name`, `password` and optionally `email`. The role creates it after the start
with the module `app_linkding_admin`, it runs the Django shell of linkding in the container as `www-data` and passes the name,
the email and the password on stdin. An existing user keeps its password if it matches, otherwise the role sets it,
the email is kept up to date and the user stays an active superuser. A changed password does not restart linkding.
The name has 1 to 150 letters, digits and `@`, `.`, `+`, `-` and `_` (the names of Django).
`LD_SUPERUSER_NAME` and `LD_SUPERUSER_PASSWORD` of the image are not used, the password would be part of the environment.

```yaml
linkding_admin:
  name: 'admin'
  email: 'admin@example.org'
  password: "{{ vault_linkding_admin_password }}"
```

### Allowed variables

The role only allows the variables in `app_linkding__environment_allowed` and the secrets listed above,
it stops before any change if unknown variables or secrets are set.
This prevents unexpected behavior by accident, e.g. by a typo or a password that has to be passed as secret.
The list is generated from `bookmarks/settings/base.py` and `prod.py`, `bootstrap.sh` and `uwsgi.ini` of linkding v1.47.0
without the secrets, `LD_SUPERUSER_NAME` and `LD_SUPERUSER_PASSWORD` (the role manages the administrator)
and `LD_SERVER_HOST` and `LD_SERVER_PORT` (the address of the container, the role waits on port 9090), new versions of the image may add variables.
The check uses the environment of the container after merging `linkding_container`.

### Container

Ports, volumes, additional hosts (`etc_hosts`) and the dependencies are changed with `linkding_container`, it is merged over the default of the container.
The dependencies of the quadlet unit are lists: `requires`, `wants`, `after`, `part_of` and `binds_to` are units,
`requires_mounts_for` are paths. They are written to `[Unit]` as `Requires=`, `Wants=`, `After=`, `PartOf=`, `BindsTo=` and `RequiresMountsFor=`.
The merge is not recursive, `linkding_container.volumes` replaces the data directory,
`linkding_container.environment` replaces the environment, use `linkding_environment` instead.
For a reverse proxy, e.g. Traefik, the labels are set with `linkding_labels`.

```yaml
linkding_container:
  requires: [ 'postgresql.service' ]
  after: [ 'postgresql.service' ]
```

### Validation

The role checks before any change:

- `linkding_secrets` is a list of entries with `name`, `data` and `target` and unique names, secrets are not empty and contain no line breaks
- `LD_ENABLE_OIDC: true` has the endpoints, `OIDC_RP_CLIENT_ID` and the secret `OIDC_RP_CLIENT_SECRET`
- no secret, `LD_SERVER_HOST`, `LD_SERVER_PORT`, `LD_SUPERUSER_NAME` and `LD_SUPERUSER_PASSWORD` is set in `linkding_environment`
- booleans, integers, numbers and `LD_DB_OPTIONS` have their type, `LD_DB_ENGINE` is `sqlite` or `postgres`, values contain no line breaks
- `linkding_admin` is a dictionary with a valid name, a password and a valid email if set
- only allowed environment variables without line breaks and allowed secrets are set in the container

If `linkding_container` or `linkding_environment` is no dictionary, merging it fails before anything changes,
the same applies to a failing template in the variables, e.g. an unknown filter.

### Check mode

The role runs with `--check`, also on a host where it never ran, and reports the directories, the secrets and the quadlet unit.
The start, the wait for linkding and the administrator do not run in check mode.

### Restart and updates

linkding is restarted if it was running and a secret or the quadlet unit changed, otherwise it is started and enabled.
If the start fails, the role shows the error and the journal of the service.
Afterwards the role asks `/health` (below `LD_CONTEXT_PATH`) up to 90 times every 2 seconds, each request waits at most 5 seconds,
and shows the journal if linkding does not answer.
Updates of the image are done by `container_update` with `linkding_autoupdate_enabled: true` and `linkding_autoupdate_schedule`,
without `linkding_autoupdate_schedule` the schedule of `container_update` is used. `bootstrap.sh` migrates the database on every start.

### Migration

The role is new, there are no former variables. An existing installation keeps its data when `data` contains the former volume `/etc/linkding/data`.
`LD_SUPERUSER_NAME` and `LD_SUPERUSER_PASSWORD` move to `linkding_admin`, `LD_DB_PASSWORD` and `OIDC_RP_CLIENT_SECRET` to `linkding_secrets`,
the booleans of the environment become YAML booleans.

### Tests

The molecule scenario `default` runs the role in two [tart](https://tart.run) VMs on a macOS controller, the base VM has to be Debian 13.
The playbooks creating and destroying the VMs live in `.molecule/tart/` in the repository root.

| Platform | Test case |
|---|---|
| `molecule-linkding-default` | Only the mandatory variables and the administrator |
| `molecule-linkding` | IPv6, labels, `LD_SESSION_COOKIE_AGE`, `LD_DISABLE_REQUEST_LOGS`, OIDC with the secret of the client and the administrator with email |

`prepare` creates the podman network and pulls the image.
`check` runs `converge` with `--check` on the new VMs.
`side_effect` runs the role with `linkding_container`, `linkding_environment` and `linkding_admin` not a dictionary, `linkding_secrets` not a list,
a secret without `target`, an unknown variable, `LD_SUPERUSER_PASSWORD`, `LD_SERVER_PORT` and a secret in the environment, a string as boolean and as integer,
an unknown engine of the database, OIDC without the secret of the client, an administrator without password and with an invalid name and an unknown secret
and checks that it fails with the expected message and the quadlet unit is unchanged (tasks marked `expect ERROR`),
then it changes `LD_SESSION_COOKIE_AGE` on `molecule-linkding`, the quadlet unit changes and linkding has to restart,
and changes the password of the administrator, the module changes it without a restart,
`molecule-linkding-default` runs again without a change, the administrator is unchanged and linkding must not restart.
`verify` checks the quadlet unit with the environment and the secrets without their values, the service without automatic restarts,
the addresses, the time zone, the database and the secret key owned by `www-data`, the health check, the login with OIDC on the login page,
logs in with a wrong password, refused with 401, and the right password (the cookies are read from `Set-Cookie`, the uri module keeps no cookies of a redirect it does not follow)
and reads the bookmarks with the session of the login.

| Environment variable | Default | Description |
|---|---|---|
| `MOLECULE_TART_IMAGE` | `ghcr.io/cirruslabs/debian:latest` | Base VM or image that is cloned |
| `MOLECULE_TART_USER` | `admin` | SSH user of the base VM |
| `MOLECULE_TART_PASSWORD` | `admin` | Password of the SSH user, used to install the SSH key and for `sudo` |

```shell
cd app_linkding
MOLECULE_TART_IMAGE='debian' molecule test
```
